# 0009 — A skill declares its subagent twin; opsward generates and checks it

## Status

Accepted (2026-10-19). Closes [thorwhalen/opsward#26](https://github.com/thorwhalen/opsward/issues/26).

## Context

A skill and a subagent carry the same thing: instructions, tool needs, references. The difference is the runtime: a skill runs inline in the caller's context; a subagent runs in a fresh context and returns a summary. The maintainer's stance is reuse ("why have only a skill or only a subagent when you can have both"), and the fleet already shows the cost of not having a rule: three skill/agent pairs were hand-written twice (`crowsnest`/`crowsnest-scout`, `openloops`/`openloops-sweep`, the `prework-alignment` skill and agent), and nothing keeps a pair in sync.

Claude Code makes both directions native and cheap. An agent file under `.claude/agents/` can preload a skill through its `skills:` field, which injects the full `SKILL.md` body at startup, not just the description; and a skill can carry `context: fork` plus `agent: <type>` to run as a subagent whose prompt is the skill body. The docs state the trade-off plainly: a subagent is for work whose output would flood the main context, that needs a tool restriction, or that is self-contained and can return a summary; a skill is for procedures the caller wants to see and steer; "they can combine". `context: fork` "only makes sense for skills with explicit instructions", runs in the background with a narrower tool set, and does not see the conversation. Measured, one task run both ways: the parent's input tokens fell from 47.8k to 2.1k and the total bill from 49.5k to 21.8k (n=1); multi-agent systems use about 15× the tokens of a chat, so delegation is for bulky side work, not every call.

Other hosts have subagents but none preload a skill into one. Copilot custom agents (`.github/agents/*.agent.md`) and Gemini CLI agents (`.gemini/agents/`) are Markdown with no `skills` field; Codex agents are TOML and inherit the parent's skills; Cursor reads `.claude/agents/` for compatibility and recommends a skill for tasks that need no context isolation; Devin's skills have `subagent: true` / `agent:` frontmatter, the closest analogue to `context: fork`; the Agent Skills spec names "subagent delegation" as an optional client pattern and mandates nothing. The spec allows arbitrary string pairs under `metadata`, and every host ignores keys it does not know. Full sources: `misc/docs/research/skills_as_subagents_briefing.md` and `misc/docs/research/skill_tiering_and_reachability.md` §4 for the context-budget side.

The issue offered three options: (a) generate an agent for every skill; (b) generate only where the "keep it out of the main context" criterion holds; (c) no files, just a `CLAUDE.md` instruction that the main agent may run any skill inside a general-purpose subagent. Option (c) already works (a subagent can invoke the `Skill` tool), so it is the floor, not a decision; it loses the tool restriction, the model choice and the discoverable name. Option (a) doubles the agent roster (another listing with its own budget: Claude Code warns above 15,000 tokens of agent descriptions) for skills that are guidelines, which produce nothing when delegated.

## Decision

1. **The skill is the single source of truth, and it opts in.** A skill declares its twin with spec-legal keys under `metadata` (`subagent: "true"`, optional `subagent-tools`, `subagent-model`, `subagent-reply-lines`, `subagent-name`), quoted so the spec's string-only map is honoured by strict validators; opsward accepts them unquoted too. Nothing is declared in the agent file that is not derivable from the skill. Other hosts ignore the keys; the skill stays portable. A declaration that cannot be rendered (no description, an invalid name, a reply budget under 1) and two skills claiming one twin name are reported by `maintain`, not rendered.
2. **opsward renders the twin and checks it.** `opsward generate` emits `.claude/agents/<name>.md` for every declaring skill (the declaration is the evidence, per ADR 0006), never overwriting. The twin preloads the skill (`skills: [<skill>]`), restricts tools (default `Read, Grep, Glob, Bash`), optionally pins a model, and states the reply contract (default: at most 5 lines, longer output in a named file, never raw command output). It carries a marker line with a hash of what it was rendered from. `opsward maintain` reports, under `subagent_twin`, a declared twin that is missing or stale and a hand-written agent that duplicates a skill (same name, or preloading it) without a declaration; `opsward diagnose` prints the twin counts in the Setup component without moving the score. All three read one pure module, `opsward/subagents.py`.
3. **The criterion is (b), applied by judgment, recorded by declaration.** A skill earns a twin when it is a task (imperative steps ending in a report) and at least one of: bulky or read-heavy work, a tool restriction, a different model or background execution, or an existing hand-written twin. Guidelines, conversation-dependent and step-by-step skills stay inline only. The shipped `opsward-subagents` skill applies the criterion to a repo, writes the declarations and runs the generator; `opsward maintain` alone is the check mode the fleet sweep runs per repo.
4. **Naming.** The twin takes the skill's name unless `subagent-name` says otherwise: one concept, two runtimes. The docs do not define the two namespaces, but same-name pairs coexist in practice (`prework-alignment` is both a skill and an agent in this fleet) and the `@name (agent)` mention form disambiguates. Existing hand-written pairs keep their names until their owner converges them; the check reports them, it does not rename.
5. **`context: fork` is the alternative for skills that are only ever delegated.** It removes the inline option, so the generated twin is preferred when the skill is useful both ways. A skill with `context: fork` needs no twin and the check does not ask for one.
6. **Cross-host, v1 is Claude Code only.** There is one renderer, for `.claude/agents/`; no host seam is declared until a second renderer exists (architecture-first: a seam needs a replacement you can point at). A Copilot renderer would emit `.github/agents/<name>.agent.md` with the skill body inlined, because Copilot cannot preload one; the declaration format would not change for it.

## Consequences

- One edit in the skill, one `opsward generate --write`, and the skill is usable in its own context, with the two kept in sync by a check that runs wherever `opsward maintain` runs. The three hand-written pairs in the fleet become findings, not folklore.
- A twin adds an entry to the agent roster, which has its own listing budget; the criterion exists so that not every skill pays it. The twin's description is the skill's, so a description written for inline triggering also has to read as a delegation trigger, and editing it makes the twin stale until it is regenerated.
- A generated twin is a described agent, so the Setup component credits it like any other agent (the note itself carries no points). Declaring twins is therefore a way to raise a Setup score; the criterion, applied by judgment, is the guard.
- `generate` never overwrites, so refreshing a stale twin is delete-then-generate; the marker line makes the generated file safe to delete.
- The fleet sweep ([thorwhalen/priv#155](https://github.com/thorwhalen/priv/issues/155)) gains a per-repo check with no new command; the `skill-package-setup`, `wads-skillify` skills and epythet's "For AI agents" page carry the rule so authors meet it where they work.
- Rejected: generate for every skill (roster bloat, guideline skills produce nothing when delegated); `CLAUDE.md`-only instruction (already true, but loses tools, model and name); a translator in the `skill` package (the twin is a `.claude/` artifact derived from a repo's own skills, which is opsward's generate/maintain charter; `skill` keeps the layout policy).
