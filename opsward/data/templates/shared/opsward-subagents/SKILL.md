# Reuse skills as subagents

A skill and a subagent are the same instructions in two runtimes: inline, in the caller's context, or delegated, in a fresh context that returns a summary. Claude Code preloads a skill's full body into a subagent through the agent file's `skills:` field, so a skill that is worth delegating needs only a thin twin: name, description, tools, model, the preloaded skill, and a reply contract. The source of truth stays in the skill; opsward renders the twin and checks it stays in sync. The decision record is `misc/docs/decisions/0009-skills-declare-their-subagent-twin.md` in the opsward repo.

## When a skill should also be a subagent

A skill earns a twin when it is a **task** (its body is imperative steps that end in a report, not conventions or guidelines) **and** at least one of these holds:

- its work is bulky or read-heavy: it scans many files, reads transcripts or logs, runs commands with long output, or reads references that the caller never needs to see ("keep it out of the main context");
- it needs a tool restriction the caller does not have, such as read-only auditing or no network;
- it should run on a cheaper or different model, or in the background, or repeatedly within one session (a status check, a sweep);
- a hand-written agent with the same job already exists, so the two can drift.

A skill that is guidelines ("follow these conventions"), that needs the caller's conversation to make sense, or that the caller must steer step by step, stays inline only. A skill that is **only** ever a delegated task can instead carry `context: fork` and `agent: <type>` in its own frontmatter; that removes the inline option, so prefer the twin when the skill is useful both ways.

## Procedure

1. **See what opsward already knows.** From the repo root:

   ```bash
   opsward maintain . --format json
   ```

   Findings with category `subagent_twin` name a skill that declares a twin that is missing or stale, or a hand-written agent that duplicates a skill. `opsward diagnose .` prints the twin counts in the Setup component.

2. **Inspect the candidates.** For each skill under `.claude/skills/` (or the package's real skill location that `.claude/skills` links to), read `SKILL.md` and apply the criterion above. Write the decision for every candidate in one line each; "stays inline" is a valid decision and is worth recording in the PR.

3. **Declare the twin in the skill**, under the spec's `metadata` map (other hosts ignore these keys):

   ```yaml
   metadata:
     subagent: true
     subagent-tools: Read, Grep, Glob, Bash   # optional; this is the default
     subagent-model: sonnet                   # optional; omitted = host default
     subagent-reply-lines: 5                  # optional; the reply contract
     subagent-name: <name>                    # optional; default = the skill's name
   ```

   Keep the description as it is: the twin reuses it, so it must already say when to delegate.

4. **Generate.** `opsward generate .` shows the twin files it would create; `opsward generate . --write` creates them. opsward never overwrites: to refresh a twin reported as stale, delete the generated file (it carries a `generated by opsward` marker line) and run `--write` again. A hand-written agent that should become generated is handled the same way, once its extra content has been moved into the skill.

5. **Check.** `opsward maintain .` must report no `subagent_twin` finding. For the fleet sweep, this command alone is the check mode: run it per repo and collect the findings.

6. **Report**: which skills gained a twin and why, which were left inline and why, and the generated paths.

## Reply contract when run as a subagent

Reply in at most 5 lines: the decisions (declared / left inline / refreshed), the paths generated, and anything the caller must still do. Put the per-skill reasoning in the PR description or a file and name its path. Never return raw command output.
